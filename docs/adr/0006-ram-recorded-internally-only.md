# ADR-0006: 호스트 RAM은 내부 근거로만 기록하고 진단 항목으로 노출하지 않는다

**상태**: Accepted (2026-08-07)
**관련 Issue**: #27 (기록 도입) · #19 (같은 PR) · [ADR-0005](0005-pre-written-result-over-exit-code.md)(사전 기록 구조)

## 맥락

Preflight는 VRAM만 본다. 그런데 두 방향에서 *"RAM도 봐야 하지 않나"* 라는 질문이 나온다.

**① 사용자에게 알려주는 쪽** — 실제 학습은 VRAM만 쓰지 않는다. 그런데 **canary는 RAM을 많이 쓰는 부분을 아예 재현하지 않는다.**

| | 실제 학습 | canary |
|---|---|---|
| 데이터셋 로딩·토크나이징 | 수 GB | ❌ |
| DataLoader worker 프로세스 | 여러 개가 각자 배치 준비 | ❌ |
| CPU offload | 켜면 옵티마이저 상태가 RAM 상주 (수십 GB) | ❌ |
| 로딩 방식 | `low_cpu_mem_usage=False`면 가중치를 통째로 RAM에 | 해당 없음 |

```
VRAM = f(모델 모양, batch_size, seq_len)        ← 전부 사용자가 명령줄로 알려주는 값
RAM  = f(로딩 방식, 데이터셋, DataLoader, offload)  ← 전부 사용자 학습 스크립트 안에 있는 값
```

**canary가 잰 RAM은 실제 학습의 RAM을 대표하지 못한다.** 사용자 스크립트를 읽지 않기 때문이고, 읽는 것은 FR-14(향후) 범위다.

**② 우리가 원인을 좁히는 쪽** — [ADR-0005](0005-pre-written-result-over-exit-code.md)에 이런 한계가 있다.

> OOM이 프로세스 강제 종료로 나타나는 경우는 `oom`으로 확정할 수 없어 `error`가 된다

| 죽는 방식 | 지금 | |
|---|---|---|
| VRAM 부족 → `torch.cuda.OutOfMemoryError` 예외 | `status="oom"` | ✅ 잘 잡힘 |
| **예외조차 없이 프로세스 즉사** | `status="error"` | ❌ **원인 후보가 여럿** |

후보는 호스트 RAM 부족(Linux OOM killer), 드라이버 크래시 등이다. 지금은 어느 쪽인지 구분할 방법이 없다.

**두 질문은 같아 보이지만 답이 다르다.** ①은 canary가 대표성 없는 값을 재는 문제고, ②는 우리 프로세스가 죽기 직전 상태를 기록하는 문제다.

## 결정

**RSS 최고점을 재되, [사전 기록](0005-pre-written-result-over-exit-code.md)에만 남기고 사용자에게 보이는 곳에는 쓰지 않는다.**

- 자식은 사전 기록을 남길 때마다 **그 시점까지의 최고점을 다시 잰다**(`rss_peak_mb`). 최종 결과에만 넣으면 정작 즉사했을 때 아무것도 안 남는다
- **현재값이 아니라 최고점**이다. 읽는 시점이 언제나 사후라 *"지금 얼마나 쓰나"* 는 의미가 없고, 커널이 최고점을 기록해주므로 주기적 샘플링 없이도 잠깐 치솟았다 내려간 구간이 남는다
- 측정 실패 시 `0`이 아니라 `None`이다 — `0`은 *"RAM을 안 썼다"* 는 뜻이 되어 정반대 결론으로 이끈다
- 의존성을 늘리지 않는다 — Windows는 `ctypes` + `GetProcessMemoryInfo`(`PeakWorkingSetSize`), Linux는 `/proc/self/status`의 `VmHWM`

### 소비자를 정확히 가른다

*"안 쓴다"* 가 어디까지인지가 헷갈리기 쉬워 못 박아 둔다.

| 소비자 | 쓰나 | |
|---|---|---|
| `judge_result` (판정) | ❌ | `verdict`에 영향을 주지 않는다. 진단 항목이 늘어나는 게 아니다 |
| `report.py` (화면) | ❌ | 숫자를 찍지 않는다. 사용자가 *"실제 학습이 쓸 RAM"* 으로 오해한다 |
| **`causes.py` (원인 분류)** | **쓸 수 있다** | **이 값의 목적이다.** `status == "error"`를 `unknown_error`로 뭉뚱그리는 대신 RAM 쪽으로 좁힐 근거가 된다 |

원인 분류에 쓰더라도 `verdict`는 그대로다 — **바뀌는 건 FIX 문구의 정확도**지 판정이 아니다. 다만 그 분류 규칙(임계값·cause 코드·문구)은 아래 "결과"의 한계 때문에 아직 만들지 않았다(#27).

## 대안

| | 왜 안 택했나 |
|---|---|
| **ⓐ 아예 안 잰다** | ②의 원인 후보를 좁힐 방법이 계속 없다. 재는 비용이 거의 0(의존성 없음, 사전 기록에 필드 하나)인데 포기할 이유가 없다 |
| **ⓑ 리포트에 표시** | 사용자가 *"canary가 쓴 RAM"* 을 *"실제 학습이 쓸 RAM"* 으로 읽는다. ①의 대표성 문제가 그대로 오해로 이어진다 |
| **ⓒ 판정 항목 추가** (RAM 부족 WARN/FAIL) | 가장 나쁘다. 대표성 없는 값으로 *"여유 있음"* 이라 해놓고 실제 학습에서 터지는 형태가 된다. 진단 도구가 낼 수 있는 최악의 오진이다 |

ⓑ·ⓒ는 **제품 범위를 넓히는 결정**이라 Notion SRS 수정이 필요한데, 대표성 문제가 풀리지 않은 상태에서 사용자에게 약속할 근거가 없다. 2026-08-06 회의에서 **Backlog Issue로만 남기고 FR 등록은 하지 않기로** 했다.

## 결과

- `status == "error"`의 원인 후보를 **한 겹 좁힐 수 있다.**

  ```
  rss_peak_mb = 30,800 / 32GB   →  우리 프로세스가 RAM을 다 먹었다
  rss_peak_mb =    900 / 32GB   →  적어도 "우리가 먹어서 죽은 것"은 배제된다
  ```

- **인과가 아니라 배제 근거다.** 값이 높다고 RAM 부족이 확정되지는 않는다. 낮을 때 배제하는 쪽이 확실하다.
- **배제 범위는 "우리 프로세스"까지다.** RSS는 프로세스별 값이라, 다른 앱이 시스템 RAM을 다 쓰고 있어서 우리가 SIGKILL된 경우는 이 값이 낮게 나온다. *"머신이 꽉 찼었나"* 는 이 값으로 알 수 없다.
- **⚠ 실행 단계 도중의 증가는 못 잡는다.** 사전 기록은 각 단계에 **진입하기 전에** 쓰이므로, 실행 중 급증 후 SIGKILL로 죽으면 살아남는 값은 그 직전까지의 최고점이다. 다만 canary는 `meta` 골격 + 레이어 단위 실체화로 모델을 올려 8B에서도 RAM 증가가 375MB 수준이라(ADR-0004 측정 환경의 스파이크), 실행 단계에서 RAM이 폭증하는 시나리오 자체가 드물다.

- **OS에 따라 유효성이 다르다.** Linux는 OOM killer가 `SIGKILL`을 보내 예외 없이 죽으므로 이 경로로 온다. Windows는 RAM 할당 실패가 `MemoryError` **예외**로 잡혀 `error_log`에 traceback이 남으므로, 애초에 이 신호가 필요 없다.
- macOS는 두 측정 경로가 모두 없어 `None`이다 — MVP 지원 대상이 아니다(NFR-01, FR-11은 향후).
- 나중에 ⓑ·ⓒ로 넘어가려면 **먼저 대표성 문제를 풀어야 한다.** canary가 실제 로딩 경로와 데이터 파이프라인까지 흉내내야 하는데, 그건 *"가중치 다운로드 없음"* 이라는 FR-02의 핵심 전제와 충돌한다.

## 지금은 반쪽이다 — 남은 것 (#27)

이 결정으로 얻은 건 *"우리 프로세스가 먹어서 죽었나"* 까지고, **원인 분류를 실제로 붙이려면 두 가지가 더 필요하다.** MVP 범위 밖으로 두고 #27에 남긴다.

| | 무엇 | 왜 |
|---|---|---|
| **시스템 여유 RAM** | 자식이 사전 기록마다 함께 수집 | RSS는 프로세스별이라, *"다른 앱이 다 써서 우리가 희생됨"* 을 지금은 낮은 값으로 오판한다 |
| **부모가 자식을 폴링** | `subprocess.run` → `Popen` + 루프 | 자식은 자기 죽음을 예측할 수 없다. 부모는 죽어도 살아있으니 **죽기 직전까지** 관측한다. `gpu.py`가 NVML로 GPU를 보는 것과 같은 자리다 |

> 폴링으로 옮겨가도 **`rss_peak_mb` 필드의 이름·의미·용도는 그대로다.** 바뀌는 건 *누가 재느냐*(자식 → 부모)와 정확도뿐이라, 계약을 다시 뒤집지 않는다.
