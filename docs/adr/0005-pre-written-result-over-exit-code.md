# ADR-0005: 자식의 죽음은 exit code 해석이 아니라 사전 기록으로 판별한다

**상태**: Accepted (2026-08-04) · **관련 Issue**: #2 (W3, FR-03)

## 맥락

[ADR-0002](0002-subprocess-isolation-for-canary.md)는 canary를 subprocess로 격리하고 **"부모 프로세스가 자식의 비정상 종료(exit code, OOM 포함)를 캐치해 정상적인 진단 결과(FAIL)로 포장한다"** 고 정했다. W3에서 이걸 실제로 구현하면서 두 가지 문제를 만났다.

**첫째, 죽는 방식이 두 종류인데 대비가 하나로는 안 된다.**

- 파이썬 예외로 잡히는 실패(`ImportError`, `torch.cuda.OutOfMemoryError` 등)는 `try`로 잡아 분류할 수 있다.
- 그런데 `.so` 로드 실패는 **파이썬이 예외를 만들 기회조차 없이 SIGSEGV로 즉사**시킨다. `except`도 `finally`도 `atexit`도 돌지 않으므로, 자식이 "죽고 나서" 결과를 남기는 것이 원천적으로 불가능하다. 그리고 이 경우가 바로 ADR-0002가 지목한 대표 시나리오다.

**둘째, exit code 해석은 이식성이 없다.** 같은 네이티브 크래시가 OS마다 다르게 보인다.

| | 크래시 시 exit code |
|---|---|
| Linux | `-11` (SIGSEGV, 음수 = 시그널) |
| Windows | `3221225477` (0xC0000005, ACCESS_VIOLATION) |

`if returncode == -11:` 같은 코드는 Linux에서만 맞고 Windows에서 조용히 틀린다. NFR-01이 두 OS 네이티브 지원을 요구하므로 이 분기를 두면 플랫폼별 코드가 계속 늘어난다. 게다가 exit code는 원인을 알려주지도 않는다 — Linux `-9`는 OOM killer일 수도, 사용자의 `kill`일 수도, 컨테이너 메모리 리밋일 수도 있다.

## 결정

**자식이 각 단계에 진입하기 전에 "여기서 죽으면 이것이 정답"인 결과를 미리 기록한다.** 부모는 자식의 exit code를 해석하지 않고, 마지막으로 기록된 결과를 읽는다.

```
자식: ① 시작 직후      → "import_crash" 를 기록
      ② import 성공 후 → "error"(실행 단계 실패)로 덮어씀
      ③ 측정 완료 후   → 최종 결과로 덮어씀

부모: 자식 종료를 기다린 뒤 결과 파일을 읽는다 (exit code는 보지 않는다)
```

파이썬 예외로 잡히는 실패는 기존대로 **구간별 `try`** 로 분류한다. 즉 두 겹이다 — 잡히는 예외는 `try`가, 잡히지 않는 죽음은 사전 기록이 담당한다.

기록은 **원자적으로** 한다(임시 파일에 쓴 뒤 `os.replace`). `open(path, "w")`는 여는 순간 기존 내용을 먼저 지우기 때문에, 덮어쓰다 죽으면 미리 써둔 정보까지 함께 날아간다. rename은 파일시스템이 보장하는 원자적 연산이라 "반쯤 바뀐" 상태가 없다.

## 대안

- **exit code로 판별한다 (기각)** — 위 맥락의 이식성 문제. 그리고 exit code는 "어디서 죽었는지"도 "왜 죽었는지"도 알려주지 않는다.
- **자식이 단계 마커를 로그에 남기고 부모가 stdout/stderr를 파싱한다 (기각)** — 텍스트 파싱은 ADR-0002가 명시적으로 금지한 방식이다. 게다가 torch·bitsandbytes가 자체 경고를 stdout/stderr에 뿌려서 신호와 잡음이 섞인다.
- **`faulthandler`나 시그널 핸들러로 크래시를 잡는다 (기각)** — SIGSEGV 핸들러 안에서 안전하게 할 수 있는 일이 거의 없고, Windows에는 POSIX 시그널이 없어 결국 플랫폼별 코드가 된다.
- **파이썬 예외만 처리하고 즉사는 포기한다 (기각)** — 그 즉사가 ADR-0002가 잡으려던 대표 시나리오(`.so` 로드 실패)다. 포기하면 격리를 만든 이유의 절반이 사라진다.

## 결과

- 자식이 **어떤 방식으로 죽어도** 부모는 항상 정규화된 진단 결과를 받는다. 진짜 세그폴트(`ctypes.string_at(0)`)와 `os._exit()` 양쪽으로 검증했다.
- **부모 코드에서 OS별 분기가 사라진다.** exit code를 해석하지 않으므로 Linux/Windows 차이가 설계 수준에서 무의미해진다(NFR-01).
- 결과 파일 쓰기가 3회로 늘지만, 파일은 수백 바이트고 canary 실행 시간은 torch import 오버헤드(3~10초, [architecture.md](../architecture.md) §6-03)가 지배하므로 무시할 수준이다.
- **한계**: 사전 기록은 "어느 **단계**에서 죽었는지"만 알려준다. 실행 단계에서 프로세스가 통째로 죽은 경우, 원인이 호스트 RAM 부족인지 드라이버 크래시인지 구분되지 않아 `oom`으로 확정하지 못하고 `error`가 된다. 추측해서 `oom`이라고 적으면 사용자에게 batch를 줄이라는 엉뚱한 안내가 나가므로, 모르는 것은 모른다고 둔다. MVP에서 실제로 마주칠 VRAM 부족은 대부분 `torch.cuda.OutOfMemoryError` 예외로 잡히는 쪽이다.
- 이 기법은 `canary/worker.py` 안에 캡슐화된다 — 계약([contracts/canary-api.md](../contracts/canary-api.md))의 `status` 값은 그대로다.
