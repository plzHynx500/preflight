# ADR-0005: CI/CD 연동을 위한 CLI 종료 코드(Exit Code)를 0(PASS), 1(FAIL), 2(WARN)로 분리한다

**상태**: Proposed (2026-08-03)
**연관 이슈**: #8

## 맥락

Preflight는 터미널 사용자의 수동 확인뿐 아니라 CI/CD 파이프라인이나 온보딩 자동화 스크립트에서 프로그램적으로 진단 결과를 판별할 수 있어야 한다. 이때 모든 실패를 단일 종료 코드(1)로 반환할 것인지, 판정 단계(PASS/WARN/FAIL)에 따라 차등화된 종료 코드를 반환할 것인지를 결정해야 한다.

- `FAIL`: 모듈 로딩 실패, OOM 등 즉시 해결해야 학습을 실행할 수 있는 치명적 오류
- `WARN`: 메모리 델타 편차, CPU 대비 속도 2배 미만 등 실행은 가능하나 주의가 필요한 상태
- `PASS`: 모든 진단 정상

## 결정

CLI 명령어(`preflight check`) 종료 시 판정(`verdict`)에 따라 아래와 같이 3단계의 규격화된 종료 코드(Exit Code)를 반환한다.
- `0`: 모든 판정 항목이 **PASS**인 경우
- `1`: 최종 판정에 **FAIL**이 하나라도 포함된 경우
- `2`: FAIL 없이 **WARN**만 포함된 경우
- `--yes` 옵션으로 수정 후 재확인(`ReVerifier`) 수행 시에는 1차 판정이 아닌 재확인의 최종 판정 결과를 기준으로 반환한다.

## 대안 비교

- **대안 A: PASS(0) / 그 외 모든 문제(1)**
  - 장점: 일반적인 UNIX 명령어 방식과 유사하며 구현이 단순함.
  - 단점: 치명적인 에러(FAIL)와 단순 성능 경고(WARN)를 스크립트나 CI 파이프라인에서 종료 코드만으로 구별할 수 없음.
- **대안 B: PASS(0) / FAIL(1) / WARN(2) (채택)**
  - 장점: 자동화 파이프라인에서 치명적 오류(`1`) 시 빌드·학습을 중단하고, 경고(`2`) 시에는 로그를 남기고 작업을 속행하는 등 유연한 제어가 가능함.
  - 단점: 기본적으로 많은 CI 도구(GitHub Actions, Jenkins 등)는 0 이외의 종료 코드를 Error로 인식하므로, WARN을 속행하려면 스크립트에서 예외 처리(`preflight check || [ $? -eq 2 ]`)가 필요함.

## 결과

- CI/CD 파이프라인 및 자동화 스크립트가 Preflight의 판정 결과(FAIL vs WARN)를 명확히 구별하여 대응할 수 있다.
- 외부 CI 도구에서 WARN(`2`)이 빌드 실패로 취급될 수 있는 위험성을 `readme.md`와 `docs/contracts/cli.md`에 명시적으로 안내한다.
