# Preflight

> 파인튜닝을 시작하기 전, 지금 환경이 실제로 준비됐는지 확인합니다.

*오픈소스 · 파인튜닝 환경 진단 도구*

---

## 왜 만들었나

QLoRA 같은 경량화 기법 덕분에 개인 GPU 한 장으로도 LLM 파인튜닝이 현실적인 선택지가 됐습니다. 하지만 드라이버·CUDA·PyTorch·학습 라이브러리로 이어지는 버전 호환성과 VRAM 산정은 여전히 까다롭고, 무엇보다 **에러 없이 조용히 실패하는 경우**가 흔합니다.

- **조용한 실패** — GPU가 설치돼 있어도 실제로는 쓰이지 않고 CPU로만 연산이 도는 경우, 느리기만 할 뿐 에러가 없어 원인을 알아채기 어렵습니다. 실제로 `torch.cuda.is_available()`이 True이고 버전도 다 맞는데, 조용히 CPU로 폴백돼 RAM만 소모한 사례를 겪은 적이 있습니다.
- **VRAM 오판** — 학습은 가중치·그래디언트·옵티마이저 상태·활성값, 네 가지 메모리를 동시에 요구합니다. 앞의 셋은 모델 구조만 알면 정확히 계산되지만, 활성값과 그 부산물인 allocator fragmentation은 실행 시점의 선택에 따라 달라져 실행해봐야만 알 수 있습니다.
- **버전 체인** — 드라이버·CUDA·PyTorch·학습 라이브러리가 서로 맞물려 있어, 하나만 어긋나도 학습이 시작조차 안 됩니다.

---

## 우리의 접근 — 추측하지 않고, 실행합니다

Preflight의 핵심 아이디어는 하나입니다 — 상태를 추측하지 않고, 아주 작은 연산을 실제로 GPU에서 실행해 확정된 값을 봅니다. 탄광의 카나리아처럼요.

모델의 실제 가중치나 데이터셋은 필요 없습니다. GPU 메모리 점유량은 텐서의 값이 아니라 shape와 dtype으로 정해지기 때문에, 구조만 같은 랜덤 값으로도 진짜와 동일한 결과를 얻을 수 있습니다. 모델 config만 조회해(수 KB, 다운로드 없음) 같은 모양의 랜덤 모델을 구성하고, 작은 연산 하나를 실제로 돌려 device 배치·메모리 이동·실행 시간을 측정합니다.

```
드라이버·CUDA  →  Python·학습 라이브러리  →  [ Preflight ]  →  실제 학습 실행
  (OS 레벨)          (환경 구성)              (여기서 확인)
```

---

## 핵심 기능 — 확인 → 수정 → 재확인

이 한 루프를 끝까지 완성하는 것이 목표입니다.

**01. 확인 — Canary Check**
작은 텐서 연산 하나로 device 배치, GPU 메모리 이동, 실행 시간(CPU 대비 배수)을 함께 실측해 조용한 실패까지 잡아냅니다.

**02. 확인 — VRAM 실측**
모델을 지정하면 가중치 다운로드 없이 실제 구조로 canary를 구성해 메모리 사용량을 실측합니다. 계산이 아니라 실측이라, activation 메모리와 allocator fragmentation까지 반영됩니다.

**03. 수정 + 재확인**
감지된 문제에 맞는 수정 명령어를 제시하고, 동의 시 실행한 뒤 Canary Check를 재실행해 실제로 고쳐졌는지 확인합니다.

## 언제 쓰나요 — 학습 명령어 실행 직전

`git commit` 전에 `git status`를 확인하는 것처럼, 학습을 시작하기 전 한 줄이면 됩니다. 설치 직후, 드라이버 업데이트 직후, 팀 온보딩·CI 스크립트에 넣어두는 것을 권장합니다.

```
$ preflight check

✔ GPU/드라이버/CUDA 체인        정상 인식 (torch.cuda.is_available()=True)
✖ bitsandbytes 4bit 레이어      device=cpu 감지 → 조용한 CPU 폴백
✖ 실행 시간 1.1배                CPU 대비 유의미한 가속 없음 (2배 미만)

FIX(제안): pip install bitsandbytes --upgrade --force-reinstall
```

### CI/CD 연동 및 종료 코드 (Exit Code)

Preflight는 CI/CD 파이프라인이나 자동화 스크립트에서 프로그래밍 방식으로 결과를 판단할 수 있도록 규격화된 종료 코드를 반환합니다. `--yes` 옵션으로 수정 및 재확인 수행 시에는 재확인의 최종 판정 결과를 기준으로 반환합니다.

| 종료 코드 | 판정 | 설명 |
|---|---|---|
| `0` | **PASS** | 모든 판정 항목이 정상 |
| `1` | **FAIL** | 최종 판정에 FAIL이 하나라도 포함된 경우 |
| `2` | **WARN** | FAIL 없이 WARN만 포함된 경우 |

> **CI 연동 시 주의사항**: GitHub Actions, Jenkins 등 대부분의 CI 도구는 `0`이 아닌 모든 종료 코드(`1`, `2`)를 파이프라인 실패(Error)로 간주합니다. WARN(`2`) 판정 시 파이프라인을 중단하지 않고 계속 진행하려면 아래와 같이 셸 스크립트에서 종료 코드를 분기 처리해야 합니다.
> ```bash
> preflight check || [ $? -eq 2 ]
> ```

## 누구를 위한 도구인가

- **설치가 막힌 사용자** — 파인튜닝 도구 설치 자체가 환경 문제로 실패해, 학습 도구 화면조차 보지 못한 초심자
- **확정값이 필요한 사용자** — "문제가 있을 수 있다"는 추정이 아니라, 실제로 문제가 있는지 확정된 답이 필요한 사용자
- **특정 생태계에 묶이고 싶지 않은 팀** — 여러 학습 도구 중 무엇을 쓰든, 그 전에 공통으로 거치는 검증을 원하는 연구팀
- **환경 변경 이후** — 드라이버 업데이트, GPU 교체, 더 큰 모델로 전환한 뒤 매번 실측으로 다시 확인하고 싶은 사용자

---

## 기대 효과

- 몇 시간 걸리는 학습이 환경 문제로 중간에 실패해 시간과 전력을 낭비하는 상황을 사전에 줄입니다.
- 버전 호환성이나 VRAM 계산처럼 스스로 진단하기 어려운 부분을 자동으로 검증해, 인프라 지식이 부족한 초심자도 안전하게 로컬 파인튜닝에 도전할 수 있도록 돕습니다.
- 어떤 학습 도구를 선택하든, 그 이전 단계에서 먼저 거쳐가는 공통 검증 관문으로 자리잡는 것을 목표로 합니다.
