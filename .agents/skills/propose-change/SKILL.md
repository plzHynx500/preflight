# propose-change

기획대로 만들 수는 있지만 위험하거나, 실제 사용성이 예상과 다르거나, MVP 범위를 줄여야 할 때
코드만 조용히 바꾸지 않고 변경안을 먼저 작성한다.

## 절차

1. 기존 요구사항과 발견한 제약을 비교한다.
2. 변경하지 않을 때의 위험을 설명한다.
3. 최소 세 가지 선택지를 제시한다.
4. 권장안을 제시하지만 승인 전에는 확정하지 않는다.
5. 승인 후에만 Notion, GitHub Issue, ADR을 필요한 범위에서 갱신한다.
6. 새 구현 범위가 생기면 별도 GitHub Issue를 생성한다.

## 어디까지 바꿔야 하는지 판단

| 상황 | 처리 |
|---|---|
| 내부 구현만 더 나은 방식으로 변경 | PR에 기록하고 구현 (변경안 불필요) |
| 현재 Issue의 완료 조건을 충족할 수 없음 | Issue에서 변경 제안 |
| 사용자가 받는 기능 범위가 바뀜 | Notion 기획 + Issue 수정 |
| 장기 기술 정책이 바뀜 | ADR 추가 |
| 나중에 하면 좋은 개선 발견 | 새 GitHub Issue → Backlog |
| 보안·실행 불가·데모 실패 문제 | 즉시 수정 또는 P0 Bug Issue |

## 변경 제안 형식 (Issue 댓글)

```
## 요구사항 변경 제안

### 기존 요구사항

### 구현 검토 결과

### 제안

### 영향
- 현재 Issue 완료 조건 수정 필요 여부
- 후속 Issue 생성 필요 여부
- ADR 작성 필요 여부
```

## Notion 변경 제안 형식

제품 기획(MVP 범위, 사용자 약속)을 건드려야 할 때만 사용한다.
팀원이 `승인`이라고 답하기 전에는 실제 Notion 문서를 수정하지 않는다.

```
## Notion 변경 제안

### 대상
(페이지 / 섹션)

### 기존 내용

### 제안 내용

### 변경 이유

### 연결 항목
- GitHub Issue:
- ADR:
```

## 사용 예시

```
/propose-change

#18 구현 중 자동 수정 기능이 위험하다는 점을 발견했다.
MVP 범위 변경안을 작성해.
```
